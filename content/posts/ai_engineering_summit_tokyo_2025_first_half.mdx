## はじめに
イベントの参加記録です。

### 1. 受けた印象
Agentの活用は当たり前で、そこから更に発展しチームの一員としてAgentを組み込める、協働できる仕組み作りが今後大事になっていく。

- それをAgentが扱う際にスコープを絞ってあげる
- 複数のAgentを扱い、それを制御する仕組みを検討する
- カスタム指示、スラッシュコマンドをチームで検討する

## How Cursor Builds Cursor

### 1. 複雑な機能の構築のための仕組み

- 自分たちも開発で Cursor を使っており、コードを書く際はエージェント第一としている（エージェントとの会話が左側、コードが右側）
- バグ修正に関して、複数のモデルを使って修正結果の比較ができる

### 2. エンジニア組織として早く動くための仕組み

- Composer の処理が高速であるため、Claude Opus で設計し、Composer で実装など効率を求めた使い分けができる
- 統合ブラウザにより、Web 開発を効率化できる。より視覚的に要素変更ができるよう、デザインツールのような画面を開発中
- コーディングエージェントが自己解決できるようにし、かつ沢山の情報を与えすぎないこと。最小限の質の高いコンテキストを用意することが大事
- bot による自動化に取り組むようになった。PR に対してバグを見つけてくれるなど。
- 大きな規模のリファクタリングに対しても、計画を作成し複数のエージェントを稼働させることで大幅な時間短縮ができる
- 統合ブラウザにより、同じ画面になるまで修正を繰り返してもらうことが可能

## GitHub Copilot 進化の最前線：AI ネイティブ組織へのステップ

### 1. GitHub について

- GitHub は単なるコードホスティングではなく、チームのコラボレーション基盤として進化してきた。
- AI 時代ではさらに、人間＋エージェントが同じチームで働く前提の“開発のホーム”へ再定義されつつある。

### 2. AI ネイティブ組織とは

- 各プロセスで AI を使っているだけでは不十分。
- AI（特にエージェント）が入ることで：
  - コードが増える
  - それに伴い タスク（レビュー、運用、テスト、ドキュメント等）も増える
  - 全体を支える仕組み・役割・運用が必要

### 3. 開発組織が本当に必要としてきたこと

- 「ツールが欲しい」ではなく、根底には：
  - 大規模でも破綻しない協働の仕組み
  - 誰が何をしているか追える可視化と履歴
  - 非同期で進めるための合意形成・記録

### 4. AI 時代の GitHub 再定義

#### 4.1 すべての開発者とエージェントのためのホーム

- エージェントがチームに入ってくる前提。
- **Agent HQ**（Copilot だけでなく他モデルも扱う方向：Claude/OpenAI 等）
  - GitHub が協働の土台である以上、複数モデル対応は自然

#### 4.2 Mission Control（タスク割当・並列実行・管理）

- 課題：エージェントに
  - どう指示し
  - どう並列に走らせ
  - どう管理・統制するか
- 方向性：複数エージェントを“チーム”として管理し、人間がオーケストレーションする。

#### 4.3 Agent Sessions（並列作業のための UI/導線）

- Agent Sessions のようなタブで、複数エージェントへアクセスし並列開発。
- 連携先：CLI / IDE / Mobile / Slack / Teams / Custom Agents 等
- github.com を中心に連携と履歴を集約していく。

#### 4.4 会話と履歴の重要性（Slack 連携例）

- 人によって使うツールが変わるほど、「どこで何が動いているか」が追えなくなる。
- 会話履歴・実行履歴がないと統制できないため、ここを押さえにいく流れ。

#### 4.5 BYOK / Bring Your Own Model

- Copilot に自前モデルを持ち込む（BYOK）方向性。
- 組織要件（セキュリティ、ガバナンス、コスト、性能）に対応。

### 5. エージェントと協働するとは（組織側の条件）

- 協働しやすい組織が求められる：
  - AI が理解しやすい形（ドキュメント、ルール、仕様）があるか
  - 人間がボトルネックになっていないか（レビュー待ち等）
- “自分の裏で勝手に動く存在”ではなく、チームの一員として扱う設計が重要。

### 6. エージェントは究極のオープンソース消費者

- エージェントは大量のコード/情報を参照して成果を出す＝ OSS 消費者。
- そのため社内でも：
  - **InnerSource（社内 OSS 的運用）**
  - 適切な管理（履歴、レビュー、再利用性）
    が重要になる。

### 7. オープンソースと AI：鍵はドキュメンテーション

- 重要なのは「いかにドキュメント化し、AI に分からせるか」。
- エージェントを“人間扱いする”＝
  - 読める仕様
  - 判断根拠
  - 手順
    を残す文化が、AI ネイティブにつながる。
- 人間レビュー工数が増えやすいので、車輪の再発明を避ける仕組みが必要。

### 8. People / Process / Product：People が軽視されがち

- AI 導入はプロダクトや自動化だけでなく、
  - チームへの溶け込み方
  - 合意形成
  - 履歴の残し方
    など People の設計が重要。
- “Person”ではなく“People”（チーム全体最適）で考える。

### 9. AI ネイティブ化の実務：カスタム指示・プロンプト・ツール・エージェント

#### 9.1 カスタム指示（最初の一歩）

- チームで合意して決めるのが重要。
- 言語/ディレクトリ単位で適用可能。
- docs 等は lint で縛りにくいので、指示で品質を寄せる価値が高い。
- 「全部高優先度」は無意味 → 優先度付けが必要。

#### 9.2 プロンプトファイル（反復作業の型化）

- チームが繰り返し使う“コマンド”をプロンプトとして固定化。
- スラッシュコマンド等の自作で、組織の反復業務を効率化。
- 個人最適に寄りがちなので、**組織へ浸透させる設計**が論点。

#### 9.3 MCP / Tools（使う道具を定義して E2E を楽に）

- 利用ツールを設定し、エージェントが E2E テストやシナリオ追加を支援しやすくする。
- 最初は広めに、運用で絞る。
- 非エンジニアにも展開しやすい形になりうる。
- 目的：暗黙知の形式知化（「何をしたいか」を AI に伝える）。

#### 9.4 カスタムエージェント（組織固有の知見を埋め込む）

- エディタ内だけでなく github.com にも広がる流れ。
- 組織固有エージェントで：
  - ルール策定
  - 仕様策定
  - 技術計画
    などを支援。
- ワンショットはプロンプトでよいが、
  - 人格/役割を固定したい
  - 複数エージェントをオーケストレーションしたい
    場合はエージェント化＋ handoff が有効。

### 10. 将来像

- GitHub workflow が agentic workflow へ（Continuous AI 的な方向）。
- DevOpsワークフローを自然言語で記述し、GitHub Actions 等を生成・運用していく。
- ゼロコンフィグ化が進み、最終的に「暗黙知」依存を減らすのが狙い。

## Findy AI+の開発、運用における MCP 活用事例・LangChain/LangGraph を活用した AI プロダクト開発の実践

### 1. MCP 活用事例（開発・運用の具体例）

#### 1.1 PR 自動作成

- Issue 内容を LLM に渡す
- GitHub MCP を使い、PR を自動生成（タイトル含む）

#### 1.2 不具合の自動修正

- Sentry MCP で Issue 情報を取得
- 原因調査 → 実装コード＋テストコードの修正まで自動化
- スラッシュコマンド化もしやすい（運用に組み込みやすい）

#### 1.3 MCP サーバーを内製・エコシステム化

- MCP 公式 TypeScript SDK を利用
- Nx で雛形 →monorepo で複数 MCP サーバーを管理
- 短期間で複数（例：10 個）サーバーを用意できる体制
- 例：レビューコメント傾向分析
  - MCP サーバーが GitHub API を実行
  - LLM が扱いやすい形に前処理して責務分離
  - レビュー指摘の取りまとめを支援

### 2. Findy AI+の開発

#### 2.1 課題意識

- 生成 AI の「使いこなし」に個人差が出る
- 使えていない理由の分析、浸透施策、投資判断が難しい

#### 2.2 提供価値

- 利活用度の可視化
- EM 向けにデータを蓄積 → 現場データを CTO 等にも展開可能に

#### 2.3 提供形態（α→β）

- アルファ版
  - リモート MCP サーバーとして提供
  - 設定ファイル追記だけで利用（MVP 志向）
  - UI を持たず、データ取得・加工に集中
  - 分析はクライアント側 LLM に寄せる
  - MCP 側に「プロンプトを用意する」機能も持たせた
- ベータ版
  - ユーザー向け画面を提供
  - サービス管理機能はローカル MCP サーバーで実現

#### 2.4 管理機能も MCP で

- 画面実装を減らせる
- 運営チーム PC で clone→ ローカル MCP 起動
- 自然言語ベースで管理機能を実現（動的プロンプト生成）
- 課題：操作/入力ミス、MCP とのやり取りが一方通行になりがち
- 対応の方向性：Elicitation（confirm/approve の挿入）
  - 確認ダイアログ等で安全に操作できる

### 3. Findy Insights の開発

#### 3.1 得られた効果

- 生成 AI でプロトタイプ開発が高速化
- 合意形成の回転数が上がる（実物で議論できる）
- 既存バックエンドチームの知見を活用し、安定性に寄与

#### 3.2 プロダクト概要（新規事業開発組織向け）

- デリバリーは速いが、ディスカバリーがネックになりがち
- 企画案だけでなく、結論に至る経緯の分析も支援する狙い

#### 3.3 内部処理（データ基盤の概略）

- 音声・テキストを S3 へ → 文字起こし → PostgreSQL
- RAG で AI エージェントに繋ぐ

### 4. 開発の進め方（時系列・チーム）

- チーム：6 名（多くが LLM プロダクト経験なし、Python 経験も薄い）
- 時系列：
  - 技術検証＋プロトタイプ作成を集中的に実施
  - キックオフ → 相談しながら実装
  - アルファ版リリース
- 実働プロトタイプを早期に作り、UX/挙動認識のズレを早期解消
- Claude Code 等で、早ければ半日でプロトタイプ作成も可能

### 5. プロトタイプ作成の型（やったこと／捨てたこと）

#### 5.1 意識したこと（PoC/プロトタイプ）

- 並列処理で処理時間を短縮 → 試行錯誤を高速化
- 細かいロギングで失敗箇所を追いやすくする

#### 5.2 捨てたこと（初期段階で割り切ったこと）

- エラーハンドリング・テスト（後回し）
- 複雑なフロント実装（処理時間が分かる程度で十分）
- 複雑なインフラ（Cloud Run でまとめてデプロイ等で簡略化）
- Figma との完全一致は狙わない（怪しい箇所のみ検証）

#### 5.3 新機能開発で意識したこと

- 既存技術スタックとの整合性
  - `claude.md` に記載して、都度プロンプトで補わなくても寄せられるように
- フロントだけでなく **データフロー** も作る
  - 処理時間の見積もり/ボトルネック把握に効く

### 6. 設計の振り返り

#### 6.1 Good

- レビュープロセスで属人化を防止
  - 運用開始後に「誰も面倒を見られない」を避ける
  - すり合わせ後にバックエンドエンジニアが実装できる状態へ
- `pgvector` を早めに用意したのが良かった
  - マルチテナント想定で Postgres 採用予定 → Postgres 寄せが合理的

#### 6.2 More

- LangChain → LangGraph への移行検討
- LLM を含む関数のテスト戦略

## コンテキスト情報を活用し個社最適化された AI Agent を実現する 4 つのポイント

### 1. 前提（なぜ「個社最適化」が重要か）

- AI エージェントの登場により、ソフトが人に合わせる方向へ
  - 業務用ソフトウェアは 最個別化の時代に入る
- 成否は 個別業務の理解 と 個別データの整備に依存
  - 特にデータ整備が重要
- ユーザー自体が変化
  - 「人間にとって使いやすい」だけでなく、AI エージェントにとって使いやすいツールが求められる
- a16z の “big ideas” でも、エージェント・フレンドリーなソフトウェアがテーマになっている

### 2. プロダクトの方向性

- 対面／電話／オンライン商談の記録を扱う
- 個社ごとに作り込める（業務に沿った分析が可能）
- AI フレンドリーなデータ構造
  - LLM が読み取りやすい形に整備する
- 階層的コンテキストデータを形成する
- 営業 AI Agent でもコーディング AI Agent でも本質は同じ
  - ドメイン知識を言語化し、構造化して渡すことが重要

### 3. 個社最適化に向けたポイント（課題と方向性）

#### 3.1 生成・プランニングの上流に「重要コンテキスト」を入れる

- 課題：商談が違えば、**注目すべき観点**も変わる
- 対応：観点を **重要コンテキストとして取得**し、その観点でプランニングさせる
  - コンテキストは下流（生成）だけでなく、**上流（計画）に効く**

#### 3.2 インデックス作成などの前処理（検索しやすさの設計）

- 課題：局所データだけでは関連性判断が難しい
  - 例：「商談 A の打ち合わせ」など、**抽象的な意味ラベル**があると検索が容易になる
- 対応：**階層的なインデックス**の活用

#### 3.3 LLM が使いやすい Tool の準備（Tool 定義と選択）

- 課題：ドメイン知識がある場合の Tool 定義
  - 例：同一取引先の商談なら過去を参照すべき、等
  - 汎用的な Tool 定義 vs 特化的な Tool 定義の両立が難しい
    - 背景：**コンテキスト圧迫**（Tool 候補が多いほど選択が難しくなる）
- トレードオフ：Tool を増やすほど便利だが、選択が難しくなる
- 対応：**Tool をフィルタリング／リランキングできる仕組み**が必要

#### 3.4 メモリマネジメント（長期的な引き継ぎ）

- 目標：真に役立つ AI Agent には 記憶の扱いが重要
- 個人最適化：
  - 次に活用できる情報を抽出し、会話や作業に引き継ぎたい
- 個社最適化：
  - 個人の記憶をさらに 組織・企業単位へ拡張することが論点

## AI エージェント構築＆運用に入門しよう！令和最新のフレームワークと鉄板ツール解説

### 1. セッションの主題

- 「AI エージェント開発」はコーディング支援の話に寄りがち
  - 理由：利用者の母数が多く、現状の LLM でも成果が出やすい
- ただし **エンジニアだけのものにするのはもったいない**
  - 一般業務の自動化にも大きな可能性

### 2. コーディング以外の AI エージェント例

- **A-BOSS**：提案資料レビュー（本部長の代わりにレビュー）
- **PharmaX**：漢方薬の相談
- **LayerX**：経費精算

### 3. RPA との違い（AI エージェントの特徴）

- 仕事を頼むと、エージェントが **自分でタスクをブレイクダウン**できる
  - 計画を立て、完遂まで試行錯誤できる
- **ツール利用**が前提
  - SaaS API を呼ぶ／社内システムを操作する等
- 仕事が終わるまで **ループ（試行 → 改善）**を続ける
- 以前（〜2 年前）：細かいワークフロー設計が必須
- 現在：**モデル性能向上＋ツール連携**で「良い感じに動く」範囲が拡大

### 4. 開発フレームワークの登場（狙い）

- Strands Agents / Mastra / LangGraph など
- 普通の Web エンジニアでも **手軽に組み込める**方向へ

### 5. フレームワーク紹介

#### 5.1 Strands Agents（AWS 系 OSS）

- 新しめのフレームワーク（AWS の商用開発でも利用）
- 特徴
  - **少ないコード（例：3 行）でエージェントが動く**
  - システムプロンプトのカスタマイズが可能
  - 任意の関数を **ツール化**できる
  - MCP 経由で便利ツールを呼び出せる
  - 複雑タスクは **役割分担してマルチエージェント**化できる
- AWS サービスとの相性が良い

#### 5.2 Mastra（TypeScript-first）

- 課題意識：PoC 後に **サーバ運用・本番移行が大変**になりがち
- TypeScript ファーストのフレームワーク（v1 beta 利用可能）
- できること（機能が“最初から多い”）
  - 多様なモデルプロバイダ + 各種ネイティブ機能へのアクセス
  - UI 開発もしやすい（AI SDK / Vercel エコシステム活用）
  - MCP / A2A / AG-UI / RAG / エージェント評価 / マルチエージェント など
- キーワード
  - **AG-UI**：軽量プロトコル
  - **Runtime Context**：実行時変数でエージェント/ツールを動的にカスタマイズ
  - **Agent Network**：複数エージェント/ワークフローが協力して動的に判断し処理
- デプロイ先の選択肢：Mastra Cloud / Vercel / Amplify / AgentCore 等
- **PoC→ 本番運用への移行がスムーズ**になりやすい

#### 5.3 LangGraph（LangChain エコシステム）

- 開発〜運用まで見据えたエコシステム
  - LangChain / **LangGraph** / LangSmith
- 特徴：低レベルで **カスタマイズ性が高い**、本番運用を意識
- LangGraph が目指す機能
  - **レイテンシ管理**（UI/UX を成立させる）
  - **信頼性**（エラーで止めず、リトライを繰り返す等）
  - **非決定性の制御**
    - 生成の揺らぎは強みでも弱み
    - Human-in-the-loop
    - トレーシング（挙動の可観測性）

### 6. 「作った後」の話：LLMOps（運用が主戦場に）

- いまは「どう作るか」より **どう運用・監視するか**に関心がシフト
- LLMOps で扱う領域
  - プロンプト設計、LLM 選択
  - トレーシング、データセット管理、オフライン評価
  - デプロイ、オンライン評価、監視・モニタリング
- 始め方（基盤）
  - クラウドベンダのプラットフォーム：AgentCore / Microsoft Foundry / Vertex AI など
- 支援ツール
  - LangSmith / Langfuse / Ragas / DeepEval

#### 6.1 Langfuse によるトレーシング例

- 検索クエリ作成 → Web 検索 → レポート生成
- 入力と出力、実行の流れが追える（可観測性）

### 7. 安全性・評価（ガードレールと計測）

- 安全性向上：ガードレールで監視
  - LLM への入力監視
  - LLM の出力監視
  - 例：Amazon Bedrock Guardrails（暴力・差別的出力などをブロック）
- 評価：実行「結果」だけでなく **軌跡（トレース）**を指標にすることが多い
  - 実行履歴の蓄積 →（Langfuse 等）→ Ragas 等で評価

### 8. 実装観点：エージェントはバックエンド、残りが肝

- エージェント（バックエンド）自体は作りやすくなった
- しかし残りの要素が重要
  - インフラ：AgentCore などのランタイムにデプロイ
  - フロント
    - Streamlit：入門向き、Python で簡単（デプロイは WebSocket 対応が要件になりがち）
    - React：Amplify Gen2 が便利（CI/CD 自動化など）
